# Building one system

This is the complete contract for building one mock system (one MCP server). Read all of it before starting.
The finished reference example is `systems/yms/`. Copy its shape.

You are done when **`python -m mockmcp check <id>` prints `ok   <id>`**.

## What you may and may not touch

- **Only create or edit files under `systems/<id>/`.** Never edit `mockmcp/`, `systems/_master/`, other systems,
  `catalog/`, `world.yaml`, tests or docs. Other builders are working in parallel.
- Do not run `git` commands. Do not install packages.
- If the engine seems to have a bug, or you need a master-data change, do not work around it by editing shared
  files: finish what you can and say so in your final report.

## Commands (run from the repo root)

| Command | What it does |
|---|---|
| `python -m mockmcp brief <id>` | Your tools (with catalogue descriptions) and every question that uses them, with follow-ups and the other tools called. **Start here.** |
| `python -m mockmcp gen <id>` | Run `gen.py`, overlay `seed/*.csv`, write `data/*.csv`. Re-run after any data or column change. |
| `python -m mockmcp run <id> <tool> '{"arg": "value"}'` | Call one tool and print exactly what the model would see. Writes are discarded. |
| `python -m mockmcp check <id>` | Lint + run every tool's example + run every scenario. Must print `ok`. |

## Files you create

```
systems/<id>/
  system.yaml       # tables + tools (required)
  gen.py            # bulk data generator (required)
  seed/<table>.csv  # hand-written rows for the question stories + reference data (required for stories)
  scenarios.yaml    # one entry per question in the brief (required)
  files/*.md        # long text (policies, reports, contract clauses), only if a tool reads documents
  hooks.py          # only for kind: py tools
  data/*.csv        # GENERATED by `gen` — never edit by hand
```

## The world

- Company: Harbour & Vale Retail Group, a UK retailer with a global supply chain. Money is GBP.
- **Data is generated around 2026-10-05 (a Monday)** (`g.as_of` in gen.py): history in the past, plans in the future.
- **At runtime every date and timestamp column is moved forward (in whole weeks) so the data ends at the real
  current date.** "Last 6 months" always has data. Therefore:
  - **Never hard-code a date in SQL, defaults or `scenarios.yaml` expects.** In SQL use the `$as_of` parameter
    (= today at runtime), e.g. `CAST($as_of AS DATE) - INTERVAL 90 DAY`; in defaults use `-90d`, `last month`, `Q3` etc.
  - In seed text (descriptions, notes, documents) prefer relative wording ("three weeks ago") over absolute dates.
  - `check` runs everything as if today were 13 weeks later, so hard-coded dates fail.
  - Ids that contain a year (e.g. `PO-2026-004512`) are not changed; that is fine.
- **Shared master data** lives in `systems/_master/data/*.csv` and is readable in SQL as `master.<table>`.
  See `systems/_master/system.yaml` for every column. Tables:
  `calendar, legal_entities, sites, locations, assets (DC equipment), products, suppliers, factories, carriers, ports, employees,
  cost_centres, partners, customers, orders, purchase_orders, po_lines, shipments, sales_weekly, dc_stock`.
- **Always use master ids** (`SKU-…`, `STY-…`, `SUP-…`, `FAC-…`, `DC1`…`DC5`, `ST001`…`ST255`, `CAR-…`, `PO-…`,
  `SHP-…`, `ORD-…`, `EMP-…`, `AST-…`, `CC-…`, `LE-…`, `PTN-…`, `CUS-…`, bins like `DC1-C-14-02`). Never invent a new
  supplier, SKU, site or PO: pick an existing one from the master CSVs (use `grep` or a tiny python snippet).
  This keeps systems consistent with each other.
- Entities the questions name already exist in master: Northampton DC = `DC1`, Daventry = `DC2`, Leeds = `DC3`,
  Store 214 = `ST214`, Style 5520 = `STY-5520`, Style 7731 = `STY-7731`, style T-4410 = `STY-T-4410`,
  SKU PF-220 (portable fan with a lithium battery) = `PF-220`, SKU K-1700 (1.7L kettle) = `K-1700`, bay C-14 = `DC1-C-14-01..04`.
- "Supplier A/B/X" etc. in questions are anonymised: choose real `SUP-…` rows and say which in `scenarios.yaml`.

## system.yaml

```yaml
id: <id>                      # exactly the system id
name: <system name from the brief>
instructions: >               # ≤ 400 chars: what the system covers + its id formats. Date and currency are added automatically.
  ...
tables:
  <table_name>:
    key: <col>                # or [col_a, col_b]
    cols:                     # ORDER MATTERS: data CSVs are written in this order
      <col>: {type: str, desc: "Short meaning, e.g. example value"}
tools:
  - ...
```

Column types: `str, text, int, float, bool, date, timestamp, enum (+ values: [...]), list`.
Quote any YAML value containing `: ` or `, ` inside `{ }` flow maps (e.g. `desc: "Site, if any"`).

### Design your tables first

- Use 2–8 tables. A table is something this system really owns (e.g. work orders, inspections, rate cards).
- Do NOT copy master tables. Reference master ids (`sku`, `supplier_id`, `site_id`, `po_id`, …) and JOIN `master.*` in SQL.
- **Name columns exactly like master columns when they hold the same thing** (`sku`, `supplier_id`, `site_id`,
  `location_id`, `po_id`, `carrier_id`, `employee_id`, …). This gives tool args free descriptions and
  automatic id/name resolution (a model can pass "Northampton DC" and it resolves to `DC1`).
- Every table needs a single primary key column (prefix ids, e.g. `WO-000123`) unless a composite key is natural.
- Include `status` columns and the columns your write tools change (e.g. `status`, `cancel_reason`, `updated_at`).
- Money columns end in `_gbp` (or carry a `currency` column). Percentages end in `_pct`.

### Tools — one entry per tool in the brief, names exactly as given

Every tool has `name`, `desc`, `kind`, `example` (args that return real rows). Choose the simplest kind that works:

**1. `select`** — list/get/search one table with filters. Args come from the filters automatically.

```yaml
- name: list_open_work_orders
  desc: Open maintenance work orders for a site, oldest first. Use to see the backlog.
  kind: select
  from: work_orders                 # own table, or master.<table>
  filters:
    site_id: {}                     # {} = equality, type/desc inherited from the column
    asset_id: {}
    status: {default: open}
    raised_from: {col: raised_at, op: ">=", default: "-90d"}   # ranges: op >= <= > <
    description: {op: like}         # case-insensitive substring
  columns: [wo_id, asset_id, status, priority, raised_at]   # optional; default all
  order: raised_at                  # SQL ORDER BY
  limit: 20                         # default rows (model can pass limit=)
  example: {site_id: DC1}
```

Lookup tools (`search_products`, `search_suppliers`, `search_sites`, …) are `select` tools over a `master.*` table
with `{op: like}` filters on the name and a few equality filters. `like` matches every word in any order:

```yaml
- name: search_products
  desc: Find SKUs by name, style, category or supplier. Returns ids to use with other tools.
  kind: select
  from: master.products
  filters:
    name: {op: like, desc: "Words in the product name, e.g. glass kettle"}
    style_id: {op: like, desc: "Style id or part of it, e.g. 5520"}
    category: {}
    supplier_id: {}
  columns: [sku, style_id, name, category, colour, size, supplier_id, status]
  order: sku
  example: {name: kettle}
```

**2. `sql`** — anything needing joins, aggregation or calculation (most `get_…_by_…`, `calculate_…`, `compare_…`, `rank_…`).
Declare `args`; optional args use the `($x IS NULL OR col = $x)` idiom; every `$name` must be an arg or `$as_of`.

```yaml
- name: get_downtime_by_asset
  desc: Total breakdown downtime hours by asset over a period, worst first.
  kind: sql
  args:
    site_id: {required: true}                    # inherits desc from column site_id
    date_from: {type: date, default: "-90d", desc: Start of period}
  sql: |
    SELECT a.asset_id, a.name, count(*) AS breakdowns, round(sum(w.downtime_hours), 1) AS downtime_hours
    FROM work_orders w JOIN assets a USING (asset_id)
    WHERE a.site_id = $site_id AND w.type = 'breakdown' AND w.raised_at >= CAST($date_from AS DATE)
    GROUP BY ALL ORDER BY downtime_hours DESC
  limit: 20
  example: {site_id: DC1}
```

`calculate_*` tools: compute in SQL (or `py`) and **return the inputs used plus the result**, and add a
`formula` column as a string literal (e.g. `'saving = (old_rate - new_rate) * volume' AS formula`).
Calculation tools may take numeric "what-if" args (e.g. `volume_units`, `rate_change_pct`) with sensible defaults.

**3. `insert`** — `create_…`, `raise_…`, `send_…`, `submit_…`, `request_…`, `log_…`. Writes a new row; every arg must be a column of the table.
`send_*`/`submit_*` store the message/request in an outbox-style table of this system (no real sending).

```yaml
- name: create_work_order
  desc: Raise a maintenance work order for an asset. Returns the new work order.
  kind: insert
  table: work_orders
  id_prefix: WO-                    # new ids are WO-000001 style
  defaults: {status: open, type: corrective}
  args:
    asset_id: {required: true}
    priority: {required: true}
    description: {required: true}
  example: {asset_id: AST-0042, priority: high, description: Mast chain worn}
```

**4. `update`** — `update_…`, `cancel_…`, `block_…`, `approve_…`, `archive_…`, `reassign_…`, `release_…`, `remove_…`, `close_…`, `delete_…`.
The key arg(s) are added automatically (named like the table key); other args must be columns.

```yaml
- name: cancel_work_order
  desc: Cancel a planned or open work order. Returns the old and new status.
  kind: update
  table: work_orders
  set: {status: cancelled}          # fixed values; "{arg}" and "$as_of" are substituted
  args:
    cancel_reason: {required: true}
  example: {wo_id: WO-900001, cancel_reason: Duplicate}
```
Add `delete: true` for real deletes (`delete_…`). Writes may target `master.<table>` only if the tool clearly
changes shared data (e.g. `update_purchase_order_delivery_date` → `master.purchase_orders`).

**5. `draft`** — `draft_…` tools. Read-only: queries + a Jinja2 template, returns text.

```yaml
- name: draft_supplier_chaser
  desc: Draft a chaser to a supplier about its late purchase orders.
  kind: draft
  args: [supplier_id]
  sql:
    sup: SELECT * FROM master.suppliers WHERE supplier_id = $supplier_id
    late: SELECT po_id, due_date FROM master.purchase_orders WHERE supplier_id = $supplier_id AND due_date < $as_of AND status IN ('open','confirmed','shipped')
  template: |
    To {{ sup[0].name }},
    These orders are past due:
    {% for p in late %}- {{ p.po_id }} (due {{ p.due_date }})
    {% endfor %}
    Please confirm new ship dates by Friday.
  example: {supplier_id: SUP-0001}
```
Filters: `money` (→ £1,234), `num(dp)`.

**6. `py`** — only when SQL is genuinely awkward (iterative/what-if maths). In `hooks.py`:
```python
def calc_payback(ctx, capex_gbp, annual_saving_gbp):     # args arrive as keyword args, already validated
    rows = ctx.q("SELECT ... WHERE site_id = $s", s="DC1") # ctx.q(sql, **params) -> list[dict]; ctx.as_of
    return {"payback_years": round(capex_gbp / annual_saving_gbp, 1), "formula": "capex / annual saving"}
```
YAML: `kind: py`, `fn: calc_payback`, `args: {...}`. Return a dict, list of dicts, or text. Never write data in py.

**Documents / long text:** put files in `files/` (markdown) with an index table (`doc_id, title, doc_type, path, …`).
Read them in SQL with `read_text('{files}/*.md')` (columns `filename`, `content`), e.g.
`SELECT content FROM read_text('{files}/' || $path)` or ILIKE search over `content`. Use
`parse_filename(filename)` to show just the file name.

### Args (applies to every kind)

- Shorthand `args: [supplier_id, sku]` inherits type/desc from same-named columns (own tables first, then master).
- Explicit: `{type, desc, required, default, values}`. Every arg needs a description (inherited or written).
- Dates accept `2026-08-14`, `2026-08`, `Q3`, `-90d`, `last 30 days`, `last month`; defaults may use these too.
  Args named `*_to`/`*_end` resolve month/quarter values to the last day.
- Args whose name is a table's key (`sku`, `supplier_id`, `site_id`, `location_id`, your own `wo_id` …) are
  resolved automatically: case-insensitive, partial or by name, with helpful "did you mean" errors.
- Keep ≤ 6 args (hard limit 8). 1–2 required. Never nested objects.
- Do not repeat the default in `desc` — the engine appends "Default X." itself.

### Descriptions (critical — a small, cheap model chooses tools from these)

- 8–25 words (lint enforces 4–30). Say what it **returns** first, then when to use it.
- If two of your tools look alike, say which to use: "Per-site totals. For one asset's history use get_asset_history."
- Use the catalogue description from the brief as the starting point; keep the meaning.

### SQL rules (lint enforces)

- Only your own tables and `master.*`. Never another system's schema.
- **Never use a system id as a table alias** (e.g. `po`, `ap`, `gl`, `fx`, `kb`, `bi`, `pim`, `oms`, `tms`, `wms`, `ims`).
  Use `p`, `pur`, `t1` etc.
- No `read_csv`. `read_text` only with `{files}`.
- DuckDB dialect: `GROUP BY ALL`, `date_trunc('week', d)`, `CAST($x AS DATE)`, `INTERVAL 30 DAY`, `round(x, 2)`,
  `string_agg(x, '; ')`, `QUALIFY`, `count(*) FILTER (WHERE …)`. Cast timestamps with `CAST(col AS DATE)` before comparing to dates.

## Data

### gen.py (bulk, realistic background)

```python
def generate(g):
    # g.rng (seeded random.Random), g.fake (Faker en_GB), g.as_of (date), g.days_ago(n), g.date_between(a, b),
    # g.weeks(n) (last n Mondays), g.master("suppliers") -> list[dict] of strings, g.pick(seq[, k])
    return {"<table>": [ {col: value, ...}, ... ], ...}
```
- Return every table (may be empty if `seed/` fills it). Keys = column names; missing columns become blank.
- Realistic volumes and noise; **≤ 20,000 rows per table** (hard cap 60,000) and ≤ 5 MB per system. Weekly grain for long history.
- Derive from master (e.g. one row per relevant PO/site/sku) so ids line up across systems.
- Deterministic: only `g.rng` / `g.fake` randomness, no `datetime.now()`.

### seed/<table>.csv (hand-written stories)

- Header = some or all of the table's columns (any order). Seed rows replace generated rows with the same key and add new ones.
- Use distinctive ids for story rows (e.g. `WO-900001`) so they never clash with generated ones.
- **For every question in your brief, plant data so that your tools return what the question needs**: the
  specific entities, numbers, anomalies and causes it mentions (e.g. "cost per unit up 9% in August" → make August
  actually 9% higher with a clear driver). The answer should be discoverable, not random.

### scenarios.yaml (required; one entry per question id in the brief)

```yaml
- question: "01:6:Q2"            # exactly the id from the brief heading
  story: What the seed data plants and how it answers the question (2-4 sentences, name the ids).
  checks:                        # at least one per question; use your tools with realistic args
    - tool: list_late_inbound_trailers
      args: {site_id: DC1, min_minutes_late: 60}
      expect: ["Midshires Transport", "190"]     # substrings that must appear in the output
```
Checks run in order against a fresh state, so a write check can be followed by a read that shows its effect.

## Workflow

1. `python -m mockmcp brief <id>` — read every question carefully.
2. Read `systems/yms/` (reference), and `systems/_master/system.yaml` (columns you can join to).
3. Design tables → write `system.yaml` tables.
4. Write `gen.py`; run `gen`; spot-check `data/*.csv`.
5. Write seed rows for the stories; run `gen` again.
6. Write all tools (with examples). Try each with `run`, including vague inputs a small model might send.
7. Write `scenarios.yaml`.
8. `check <id>` → fix everything until it prints `ok`.

## Final report (your last message)

Keep it short: `check` result, table names with row counts, number of tools by kind, any questions you could
only partly support and why, and any engine/master problems you hit.

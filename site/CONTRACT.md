## Design: the report palette is the brand

The site uses the colourful styling of the benchmark's HTML reports and stays consistent with it. That palette lives in `mockmcp/eval/svg.py` (`_LIGHT`, `_DARK`) and reaches the site as CSS custom properties in `mm-tokens.css`:

- `:root` holds the light values, and `:root[data-theme='dark']` the dark values. Starlight always sets `data-theme` on `<html>`.
- **Surfaces:** `--mm-bg`, `--mm-surface`, `--mm-fg`, `--mm-muted`, `--mm-grid`, `--mm-axis`.
- **Outcomes (fixed meaning: never reuse one for decoration with a different meaning):**
  - `--mm-o-pass` green
  - `--mm-o-honest_fail` blue
  - `--mm-o-partial` amber
  - `--mm-o-over_cautious` violet
  - `--mm-o-fabricated` orange
  - `--mm-o-unsafe` magenta
  - The `--mm-b-unsafe_*` ramp.
- **Run sides:** `--mm-side-a` azure and `--mm-side-b` plum, for "run A vs run B" (e.g. Haiku vs Sonnet).
- **Text on a mark:** `--mm-ink-<mark>` gives a contrasting ink.
- **Font:** `--mm-font` (system stack). No web fonts, no external scripts or stylesheets.
- **Usage:**
  - Use colour as the reports do: to encode meaning (outcomes, sides).
  - Decoration (hero, accents) may use the outcome colours together as a spectrum, e.g. the stacked outcome bar as a brand stripe. A single outcome colour must not imply something false.
  - `src/styles/theme.css` maps Starlight's `--sl-color-*` onto these tokens, so docs pages, the landing page and the reports read as one product. Package A owns it.
- **Requirements:** UK English, light and dark, no horizontal scroll at 375 px, text contrast ≥ 4.5:1.

- The sidebar groups in `astro.config.mjs` are Get started, Examples and Reference. Order pages with `sidebar.order` in frontmatter, not in the config.
- **Route clash:** `public/examples/<name>/` and the docs page `/examples/<name>/` share a folder. The docs page is `index.html` there, and the report files sit beside it, so `/examples/haiku/report.html` and the page `/examples/haiku/` coexist. The `public/` copy must not contain an `index.html`.

## `src/data/examples.json` (written by C, read by A and C)

```jsonc
{
  "generated_from": "docs/examples",          // provenance
  "budgets": [{"key": "tokens-0", "label": "~14k"}, ...],   // in ladder order, labels from the report
  "runs": {                                    // single-run examples, keyed by folder name
    "haiku": {
      "title": "...", "model": "...", "tool_search": false, "tasks": 800,
      "pass_rate": {"all": 0.616, "by_budget": {"tokens-0": 0.65, ...}},
      "cost_usd": {"all": 74.65, "by_budget": {...}}, "cost_per_pass_usd": 0.15,
      "outcomes": {"pass": 493, "partial": 181, ...},
      "report": "examples/haiku/report.html"          // path under BASE_URL
    }, ...
  },
  "comparisons": {                             // keyed by folder name
    "haiku-vs-sonnet": {
      "a": "haiku", "b": "sonnet",
      "pass_rate": {"all": {"a": 0.616, "b": 0.630, "p": 0.49}, "by_budget": {"tokens-0": {"a":..,"b":..,"p":..}, ...}},
      "by_kind": [{"kind": "decide", "a": .., "b": .., "delta": .., "p": ..}, ...],
      "report": "examples/haiku-vs-sonnet/compare.html"
    }, ...
  }
}
```

- Every number is read from `report.json.gz` / `compare.json.gz`. None is typed by hand.
- C may add fields. If a field above doesn't exist in the source, C names the substitute in its final report, and A reads whatever C actually wrote.
- Until C's script exists, A works against `src/data/examples.sample.json`, which C writes first.
